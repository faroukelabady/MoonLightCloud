# MoonLight Disaster Recovery Runbook (Phase 20)

Master recovery procedures. Commands are verified against the real
repositories at the Phase 20 working tree. Section numbers map to the
Phase 20 implementation prompt.

> **Naming.** `Retail` = `MoonLightRetail`. `Cloud` = `MoonLightCloud`.
> `$RETAIL` and `$CLOUD` are the two repository roots.

---

## 3. Retail backup and restore

### 3.1 Take an operational backup

Operational (disaster-recovery) backups are distinct from the Phase 18
**updater** backup. The updater backup protects the application during
an update and is deleted on success; it is not a disaster-recovery
strategy.

Interactive: Retail → Settings → Backup (requires `backup.manage`). This
application path applies the keyring and the `BACKUP_ENCRYPTION_REQUIRED`
policy, and is the supported way to produce **sealed** archives.

CLI (unattended / scheduled):

```bash
$RETAIL/recoverytool backup --db /path/to/moonlightretail.db \
  --images /path/to/product-images \
  --recovery /path/to/recovery \
  --keyring /path/to/backup.keyring
```

> **Phase 20 CLI limitation — read before relying on the CLI.** Only
> `recoverytool apply` currently reads `--keyring`. `backup`, `validate`
> and `stage` accept the flag but **ignore it**:
>
> - `backup` always writes an **unencrypted** archive, even with
>   `--keyring` and even when `BACKUP_ENCRYPTION_REQUIRED=true`;
> - `validate` and `stage` pass a nil keyring, so a **sealed** archive is
>   **refused** by them (`TestSealedRestoreRefusedWithoutKeyring`).
>
> Until this is remediated, use the **application** path to create and
> validate sealed backups. The full CLI round trip
> (`backup` → `validate` → `stage` → `apply`) works only for unencrypted
> archives.

Encrypted backups (recommended) need a keyring. It is generated with the
`internal/backupcrypto` library (`NewKeyring` + `SaveKeyring`); there is
**no CLI** to create one yet. Keep it OUTSIDE the backup destination:

```bash
# Generated by the operator; keep OUTSIDE the backup destination.
# Losing the keyring makes backups unrecoverable.
export MOONLIGHT_BACKUP_KEYRING=/secure/backup.keyring
```

Set `BACKUP_ENCRYPTION_REQUIRED=true` in production so a missing keyring
fails the backup instead of silently writing plaintext. The value is
strict: `true`/`1` enable, `false`/`0` disable, anything else is a
startup configuration error.

Retention: keep at least one copy on a **different physical device**
(an external drive or another machine). A backup on the same disk is
not disaster recovery.

### 3.2 Verify a backup before trusting it

```bash
$RETAIL/recoverytool validate --archive /path/to/backup.mlrbak
```

Validation checks: ZIP structure, per-file SHA-256, manifest parity,
SQLite `integrity_check`, `foreign_key_check`, schema compatibility,
per-table counts, stock-vs-ledger reconciliation, referenced images,
and (for sealed archives) AES-256-GCM authentication.

> `validate` ignores `--keyring`, so it can only verify **unencrypted**
> archives. Verify a sealed archive through the application path
> (Settings → Backup & Recovery) instead. (`validate` did document a
> `--keyring` flag; it has no effect.)

### 3.3 Restore (planned, shop closed)

```bash
# Unencrypted archive only — stage ignores --keyring (see §3.1).
$RETAIL/recoverytool stage \
  --archive /path/to/backup.mlrbak \
  --db /path/to/moonlightretail.db \
  --images /path/to/product-images \
  --recovery /path/to/recovery
# Restart Retail. The staged restore applies at startup, atomically.

$RETAIL/recoverytool apply \
  --db /path/to/moonlightretail.db \
  --images /path/to/product-images \
  --recovery /path/to/recovery \
  --keyring /secure/backup.keyring
```

`--db` and `--images` are required by every mutating subcommand;
`apply` **does** honour `--keyring`, so it can complete a restore of a
sealed archive that was staged by the application path.

The restore is applied during startup **before** the app accepts
business writes. It never runs while Sales are in progress.

**Wrong-Store protection:** a backup belonging to a different Store is
refused. The guard compares the immutable `store_identity` UUID —
changing a shop name is a legitimate restore and is not blocked.

**Post-update safety:** after an updated version has enabled business
operations, automatic restoration of an older pre-update database is
forbidden. Deliberate owner-initiated restore of an older backup is
allowed but warns that newer unbacked transactions are absent.

## 4. PostgreSQL backup and restore (Cloud)

### 4.1 Backup

```bash
$CLOUD/scripts/pg-backup.sh --url "$DATABASE_URL" --out /secure/backups
```

Produces `moonlight-cloud-<timestamp>.dump` (pg_dump custom format),
a schema-only companion, and a manifest with SHA-256, duration and the
schema version read from the archive itself. A reused `--label` is
refused (an existing backup is never overwritten), files are created
owner-only, and an interrupted run leaves no partial artifact.
Verification is `pg_restore --list` on the produced artifact — a
backup that cannot be read is deleted and reported as failed.

Retention: `PG_BACKUP_RETENTION` (default 7) oldest-first.

> **This is not PITR.** A pg_dump restores to the dump moment only.
> For an RPO tighter than the backup interval the provider must
> supply WAL archiving / snapshot PITR (see §5).

### 4.2 Restore drill (real, disposable)

```bash
# 1. backup
$CLOUD/scripts/pg-backup.sh --url "$URL" --out /backups --label drill-001
# 2. destroy the disposable database
psql "$ADMIN_URL" -c "DROP DATABASE drill;"
# 3. restore
$CLOUD/scripts/pg-restore.sh --url "$URL_RESTORED" --dump /backups/moonlight-cloud-drill-001.dump --force
# 4. start the exact Cloud binary and check /health/ready
```

Post-restore validation runs automatically: schema presence for
devices/stores/sync_events/catalog/sales/admin_users/releases/
update_rollouts, orphan device-binding check, and command PK
integrity.

### 4.3 Point-in-time recovery

**NOT RUN in Phase 20.** PITR requires provider-level WAL archiving
(`archive_mode=on` + a WAL destination) which is external
infrastructure. Resulting limitation: RPO equals the backup interval.

## 5. Cloud outage and resynchronization

Retail is offline-first: POS, inventory, returns and reports keep
working while Cloud is unreachable.

On Cloud recovery:
1. Restore Cloud if needed (§4.2).
2. Restart Retail connectivity — devices reconnect on their own poll
   interval.
3. Retail replays its durable outbox. Cloud reprojects idempotently
   (event IDs and revision checks are preserved).
4. Watch `/api/v1/dashboard/sync-health` backlog drain.

## 5.1 Cloud restore recovery protocol (Phase 20 R2)

A successful `pg_restore` is **DATABASE_RESTORED**, not
**STORE_RECONCILED**. Cloud can serve traffic and return `/health/ready`
200 while its business projections are historically incomplete.

The protocol is explicit and durable:

```text
1. DETECT   scripts/pg-restore.sh marks every device
            RECOVERY_RECONCILIATION_REQUIRED in sync_recovery_state.
            The state is a table: it survives Cloud restarts.
            ONLY the supported workflow marks it — see the detection
            limitation below.

2. EXPOSE   Retail reads GET /api/v1/device-control/recovery/status
            over its normal authenticated control channel. Store sync
            status reports RecoveryRequired=true with instructions;
            pending_outbox=0 is NEVER treated as proof that Cloud's
            projections are complete.

3. VERIFY   Retail opens /recovery/verify/begin with device auth, then
            captures the retained outbox count and SQLite insertion
            high-water mark together. It declares the count on page one
            and sends only rows at or below that finite boundary in
            bounded event_id byte-order pages. Every page carries the
            returned generation. New rows after the snapshot flow through
            ordinary sync; a restart opens a fresh generation and snapshot.
            Cloud returns missing identities and records server-side
            coverage; it does not trust a client missing-count claim.

4. REPLAY   Retail re-queues only delivered rows Cloud reported
            missing, at most 200 per pass, and the normal sync
            worker resends them; repeat Reconcile until zero missing. Rows Cloud permanently rejected (blocked)
            were never acknowledged and are not part of the walk. Cloud ingest is
            idempotent: duplicates ACK already_accepted; missing
            events ingest and reproject.

5. COMPLETE Retail POSTs /recovery/complete ONLY after a verification
            pass reports zero missing. Until then the device flag
            stays set and the Store is not reported reconciled.
```

Retail is the authority throughout: Cloud never writes Retail Sales,
never fabricates events, never replaces inventory and never reissues a
business mutation. The canonical event bytes are simply re-sent.

**Multi-device rule:** a Store is never labeled reconciled while any
active device of that Store is still unresolved. Each device clears its
own flag. Counts are per Store: another Store's devices and projections
never block (or appear in) this Store's report. A retired or replaced
workstation is resolved by revoking its device identity
(`moonlight-cloud device revoke <device-id>`); its retained history is
verified by the replacement device from the restored Retail database.

**Projection convergence:** completing verification proves *event
history*, not business projection. `projections_pending` counts Cloud
accepted events of this Store whose required processor has not reached
`processed` (including events not yet claimed by any processor).
A Store is reconciled only when
`devices_unresolved == 0 && projections_pending == 0`. Never infer
reconciliation from `/health/ready`, from `required=false` alone, or from
a non-zero delivered count.

**Operator actions:**

```bash
# 1. Restore Cloud with the supported workflow (marks recovery state)
$CLOUD/scripts/pg-restore.sh --url "$URL" --dump /backups/backup.dump --force

# 2. Confirm every device is marked
psql "$URL" -Atqc "SELECT device_id, required, reason FROM sync_recovery_state WHERE required"

# 3. On EACH Retail device, run the reconciliation protocol
#    (see "Retail reconciliation entry point" below)

# 4. Verify the flag cleared for every device AND no projections pending
curl -s -H "Authorization: Bearer $DEVICE_CREDENTIAL" \
  https://cloud/api/v1/device-control/recovery/status
#   → {"required": false, "devices_unresolved": 0,
#      "projections_pending": 0, "store_reconciled": true}

# 5. Only then report the Store as reconciled.
```

> **Retail reconciliation entry point.** The operator path is
> Settings → Cloud Sync → Cloud recovery in the MoonLightRetail desktop:
> a recovery section showing the real server-confirmed state
> (`GetCloudRecoveryStatus`) and an admin-only **Reconcile** action
> (`ReconcileCloud` binding). There is no `sync reconcile` CLI — do not
> quote one.

**Recovery marking override — `PG_RESTORE_MARK_RECOVERY` and break-glass.**
Recovery marking is **enabled by default** and is no longer controllable
through the environment: `PG_RESTORE_MARK_RECOVERY` accepts only *unset*
or exactly `1`. Every other value (`0`, `true`, `false`, `yes`, `no`,
`garbage`, empty-but-present, …) is a **configuration error** and the
script exits before touching anything.

- **Break-glass:** the only way to skip marking is two explicit CLI
  flags together — `--allow-unmarked-restore --confirm-unmarked-restore`.
  An inherited environment variable can never enable it.
- **Risk (unchanged):** with marking skipped, a restored Cloud returns
  `/health/ready` 200 and appears healthy while acknowledged business
  projections are missing and **no device is flagged**. The script prints
  a prominent break-glass banner, reports
  `RECOVERY_MARKING_COMPLETE = NO`, and **never claims `STORE_RECONCILED`**.
- **Recommended use:** only for a deliberate disposable lab/test restore
  that you will verify by other means. **Never use it in production.**
- **Marking failure fails the operation:** if the per-device writes do
  not take effect (wrong schema, silent no-op, partial write), the script
  exits nonzero and reports `DATABASE_CONTENT_RESTORED = yes` alongside
  `RECOVERY_MARKING_COMPLETE = NO` — the restored content is not
  undoable, and the operator is told exactly that instead of seeing a
  success message.

The environment variable can no longer bypass marking. Only the two
explicit CLI flags together can, and they announce themselves loudly.

```bash
# Normal restore: marking is on and needs no configuration.
$CLOUD/scripts/pg-restore.sh --url "$URL" --dump /backups/backup.dump --force

# Disposable-lab break-glass ONLY — never in production:
$CLOUD/scripts/pg-restore.sh --url "$URL" --dump /backups/backup.dump --force \
  --allow-unmarked-restore --confirm-unmarked-restore
```

**If retained history is unavailable** (the Retail database itself was
replaced and the delivered rows are gone), automatic recovery is
impossible. That case is reported as **recovery-blocked**: the operator
must not be told "fully recovered" when canonical events are missing.

**Retail restored older than Cloud (§7 scenario C):** a restored Retail
backup may lack Sales that Cloud already projected. Those Sales are
**data loss from Retail's side**. The system does NOT import Cloud
projection rows back as new Retail Sales or inventory movements, and it
does **not** detect this case automatically: Retail and Cloud both report
healthy. The operator must compare the Cloud Sales list for the period
after the backup with the restored Retail records and record the absent
transactions manually. Cloud keeps showing the higher inventory revision
until Retail's own revision for that Variant passes it again (subsequent
stock changes); until then the Cloud stock projection is stale and must
not drive online allocation.

### 5.2 Detection limitation (do not assume automatic detection)

Recovery marking happens **only** in the supported restore workflow
(`scripts/pg-restore.sh`). The following do **not** set the marker and are
**not** detected:

- manual `pg_restore` / `psql` restore;
- `pg_basebackup` or a filesystem snapshot;
- managed-service point-in-time recovery;
- replica promotion;
- vendor/panel snapshot restores.

Such a restore is indistinguishable from a healthy Cloud to this
mechanism: `/health/ready` is 200, projections are internally consistent,
and yet acknowledged events may be absent. If you restore Cloud by any
other means, first run `moonlight-cloud migrate up` (schema 45 or later),
then mark the devices yourself (the statement also starts a fresh
verification generation) and run reconciliation:

```bash
psql "$URL" -Atqc "SELECT id FROM devices" | while read -r dev; do
  [ -z "$dev" ] && continue
  psql "$URL" -q -c "INSERT INTO sync_recovery_state
    (device_id, required, reason, started_at, updated_at)
    VALUES ('$dev', TRUE, 'cloud database restored from backup', now(), now())
    ON CONFLICT (device_id) DO UPDATE SET required = TRUE,
      reason = EXCLUDED.reason, cleared_at = NULL, updated_at = now(),
      verify_generation = sync_recovery_state.verify_generation + 1,
      verify_last_event_id = '', verify_pages = 0, verify_events = 0,
      verify_complete = FALSE, verify_declared_total = 0, verify_missing = 0"
done
```

**Backups taken before Phase 20 (schema < 45).** Every backup taken before
the Phase 20 release is schema 43 or 44 and has no (or an older) recovery
ledger. `pg-restore.sh` reads the archive's schema version **before** any
destructive step and refuses with exit 10 unless you pass
`--cloud-binary <moonlight-cloud binary of the release you will run>`. With
it, the script restores, runs `migrate up` with that binary (run the script
with the release's production environment), validates, and then marks
every device. A migration failure after restore exits 12 and reports
`DATABASE_CONTENT_RESTORED = yes`, `RECOVERY_MARKING_COMPLETE = NO`.

**Partial failures are reported, never hidden.** A `pg_restore` error exits
11 with `DATABASE_CONTENT_RESTORED = PARTIAL / UNKNOWN`; a failed
post-restore validation exits 7 and states that the content is already
restored and devices are not flagged; a target that cannot be inspected is
refused (exit 3) before anything is changed.

### 5.3 Verification constraints and trust boundary

Cloud owns the completeness proof. A verification pass is recorded in the
`sync_recovery_state` coverage ledger, and `/recovery/complete` is
refused unless **all** of the following hold:

```text
verify_missing == 0                    the server recorded no missing identity
                                       (the client's last_missing must also be 0)
pages > 0                              never a zero-work shortcut
verify_complete == true                a page was submitted end_of_history
verify_declared_total != 0             a retained-history total was declared
verify_events >= verify_declared_total coverage reached the finite boundary
```

Each verification page must be strictly ascending by `event_id` in byte
order and start above the recorded cursor, so a replayed, repeated or
out-of-order page is refused outright. Marking a device (again) starts a
fresh generation: an earlier completed ledger can never be reused.

Completion is tied to the exact verification generation that was read. The
database checks the generation, complete-page marker, effective lower-bound
total, coverage of at least that total, and zero-missing ledger in the same
conditional write that clears the device flag. Retail opens a generation
before taking its local snapshot. Cloud captures its accepted-event count
atomically at generation start; Retail then reads the retained outbox count
and SQLite insertion `rowid` high-water mark together and declares the count
on page one. It pages only snapshot rows at or below that boundary in
`event_id` byte order. The first page raises the effective lower bound to
the snapshot count when needed. New Sales and inventory events after the
snapshot continue through ordinary synchronization and projection; they do
not extend the current pass or require pausing business activity. A restart
opens a fresh generation and takes a fresh snapshot, so partial prior
coverage cannot complete. If a newer pass or restore mark starts first, an
old page/completion is rejected as stale and the device remains
recovery-required. Repeating a valid completion for the same generation is
safe. Event-history completion remains separate from projection convergence
and the Store-wide `store_reconciled` result.

Identity matches are scoped by Cloud to the authenticated device's
server-side Store binding. A bound device can verify events ingested for
that Store, including same-Store replacement-device history. An event
whose historical `store_id` is NULL is eligible only for its original
device; an unbound device fails closed and cannot use another Store's
event IDs and hashes as acceptance matches. The device cannot choose this
scope in its request. The existing trust limitation is unchanged: the
server can compare submitted identities and enforce the Cloud-known lower
bound, but it cannot cryptographically prove that a compromised trusted
client disclosed every event lost from the restored database.

**Proven:** a client claim of `missing=0` cannot clear recovery (the
server's own `verify_missing` decides); a partial walk cannot
complete; skipped/replayed pages are refused; an interrupted pass resumes
and completes only after a full walk.

**Trust boundary — hardened, with a documented residual.** `verify_declared_total`
is supplied by the device, but Cloud now refuses any declaration below the
number of `sync_events` it already holds for that device (an independent
lower bound on retained history), in addition to all prior ledger
constraints (contiguous keyset pages, one generation, terminal
end_of_history, zero missing). The supported Retail client declares its
true retained row count. Residual: a compromised device can still
under-declare down to — but never below — the Cloud-known bound for
events Cloud has never seen. See `ADR-0054` for the explicit
proven-vs-assumed table.

### 5.4 PostgreSQL backup confidentiality

`pg_dump --format=custom` is **compression and a consistent snapshot, not
encryption**. A custom-format dump contains every table's plaintext:
Sales, customers, prices, password hashes and admin sessions. Handle it as
sensitive data.

- **The dump is not confidential at rest.** Treat the backup destination
  as a sensitive system: access-controlled, and preferably encrypted at
  the storage layer (LUKS, an encrypted object store, or an
  application-level envelope).
- **Do not report the production confidentiality requirement as met**
  until external encrypted storage and its key management are actually
  provisioned. That provisioning is a **Phase 21 prerequisite**.
- `scripts/pg-backup.sh` warns that a copy on the same disk is not
  disaster recovery; it does **not** encrypt the output.
- Restrict filesystem permissions on the destination and on any transfer
  channel. Do not send dumps over unencrypted transports.

### 5.5 Operational prerequisites and RPO/RTO limits

**RPO (recovery point objective)** is bounded by the last successful
`pg_dump`, never better. `pg_dump` restores to the moment of the dump; any
transaction after it is lost unless WAL archiving is separately
configured. Plan the backup cadence against the loss the shop can tolerate.

**RTO (recovery time objective)** is the sum of: dump transfer, restore
into the target database, migration check, and reconciliation on every
Retail device. Reconciliation scales with the size of retained Retail
history and requires the sync worker to run between passes. Do not quote
an RTO that excludes reconciliation — the Store is not usable as
"reconciled" until it completes.

**Prerequisites for a real recovery:**

- the dump itself, verified (`pg_restore --list`);
- the Cloud binary and matching migration set;
- PostgreSQL 18 available;
- device credentials for every Retail device (OS keyring on each device);
- the Retail retained outbox (the Retail database) — if it is gone,
  automatic reconciliation is impossible and the case is
  **recovery-blocked** (see below).

**Phase 21 prerequisites (still external):** off-host encrypted backup
destination and key management; external secrets management; production
TLS; release-signing trust anchors; independent-destination restore
certification; live scheduled-backup verification.

## 6. Workstation replacement

```text
1. Install a verified Retail build on the new workstation.
2. Restore the operational backup (§3.3).
   - The immutable store_identity UUID carries over: it is the Store.
   - The old device credential lives in the OS keyring and does NOT
     carry over. Copying the database alone cannot revive a revoked
     device identity.
3. Validate: schema version, integrity check, inventory reconciliation.
4. Re-enroll the device in Cloud (Settings → Cloud Sync → credential).
   Cloud issues a NEW device identity; the old one stays revoked.
5. Reconnect and let sync catch up (§5).
6. Resume Sales.
```

An old revoked device identity must not become usable by copying an
old database — device authorization is server-side and revocation is
authoritative in Cloud.

## 7. Failed update and manual recovery

Phase 18 updater semantics (preserved):

- The updater takes a pre-update SQLite backup and records it in the
  journal.
- The new release runs in a **gated** state: migrations + health check
  + explicit confirmation **before** any business write.
- Rollback restores the previous install and the pre-update database —
  but **only before business operations are enabled**.
- After confirmation, automatic database restore is permanently
  forbidden. A deliberate owner restore is a disaster-recovery action
  (§3.3), not a rollback.

Journal corruption: the agent reports `MANUAL_ACTION_REQUIRED`
(`UPDATE_JOURNAL_CORRUPT`) and the helper refuses to act. The app
still starts normally on the current install.

## 8. OWNER / MFA recovery

All recovery is **CLI-only and audited**. There is no public HTTP
reset endpoint and no way for an ADMIN to gain OWNER privileges.

```bash
# Lost password (and optionally lost authenticator)
$CLOUD/moonlight-cloud auth reset-password --login <owner-login> --reset-mfa
```

Effects: new password set, MFA enrollment cleared (if `--reset-mfa`),
**every** session for that user revoked, `auth.password.reset` audited.

Lost `AUTH_MFA_ENCRYPTION_KEY`:
1. Provision a NEW key (all existing MFA ciphertext becomes unreadable).
2. Set `AUTH_MFA_ENCRYPTION_KEY` and restart.
3. Run `auth reset-password --reset-mfa` per affected user.
4. Users re-enroll MFA and receive new recovery codes.

The system fails closed: it never silently disables MFA or regenerates
credentials because a key cannot decrypt.

## 9. Credential and key rotation

| Asset | Rotation | Notes |
|---|---|---|
| Cloud TLS certificate | reverse-proxy renewal | not persisted in DB |
| PostgreSQL password | `ALTER ROLE` + config update + restart | sessions reconnect |
| Device credential | CLI `device rotate` | old credential revoked in same transaction |
| MFA encryption key | new key + `reset-password --reset-mfa` | old ciphertext unreadable by design |
| Release-signing key | overlapping trusted public keys | see runbook 10 |
| Backup encryption keyring | `AddKey` then re-seal new backups | old backups stay readable; keep the old key |

## 10. Release signing, rollout and revocation

- Generate the Ed25519 signing key **offline**. The private key is
  never packaged into Retail, Cloud or any OCI image.
- Provision the matching public key into Retail builds and Cloud via
  `RELEASE_TRUSTED_PUBLIC_KEYS`.
- Sign release envelopes offline; verify independently before import.
- Roll out through Cloud fleet updates (staged percentage).
- **Revocation:** `SetReleaseStatus` revokes a release; targets stop.
- **Key compromise:** revoke trust in the public key, publish a new key,
  and treat any release signed by the compromised key as untrusted.
- **Key loss:** publishes stop until a new key is provisioned. Existing
  installed Retail keeps working; it cannot be updated.

## 11. Incident diagnosis and support bundle

Collect a sanitized support bundle (Retail):

```
Settings → Diagnostics → Support Bundle
```

Contents: app version/build, OS, schema version, integrity-check
result, error codes, update journal summary. It contains **no**
passwords, tokens, private keys, MFA secrets, recovery codes, provider
credentials or customer records.

Cloud diagnosis: `moonlight-cloud projection status`, `/health/ready`,
`/api/v1/dashboard/sync-health`, `/api/v1/dashboard/update-audit`, and the
allowlisted support bundle `moonlight-cloud diagnostics [--out <file>]`
(versions, schema, projector counts and error codes, feature booleans; no
secrets, DSNs or business records).

## 12. Pilot readiness and rollback decision

See `docs/operations/pilot-readiness.md`. The rule: a completed Phase 20
code freeze does NOT mean the physical/operational pilot prerequisites
are satisfied. Every checklist item must be answered with evidence.

# MoonLight Disaster Recovery Runbook (Phase 20)

Master recovery procedures. Commands are verified against the real
repositories at the Phase 20 working tree. Section numbers map to the
Phase 20 implementation prompt.

> **Naming.** `Retail` = `MoonLightRetail`. `Cloud` = `MoonLightCloud`.
> `$RETAIL` and `$CLOUD` are the two repository roots.

---

## 3. Retail backup and restore

### 3.1 Take an operational backup

Operational (disaster-recovery) backups are distinct from the Phase 18
**updater** backup. The updater backup protects the application during
an update and is deleted on success; it is not a disaster-recovery
strategy.

Interactive: Retail → Settings → Backup (requires `backup.manage`).
CLI (unattended / scheduled):

```bash
$RETAIL/recoverytool backup --db /path/to/moonlightretail.db \
  --images /path/to/product-images \
  --recovery /path/to/recovery \
  --keyring /path/to/backup.keyring
```

Encrypted backups (recommended) need a keyring. Create one once:

```bash
# Generated by the operator; keep OUTSIDE the backup destination.
# Losing the keyring makes backups unrecoverable.
export MOONLIGHT_BACKUP_KEYRING=/secure/backup.keyring
```

Retention: keep at least one copy on a **different physical device**
(an external drive or another machine). A backup on the same disk is
not disaster recovery.

### 3.2 Verify a backup before trusting it

```bash
$RETAIL/recoverytool validate --archive /path/to/backup.mlrbak \
  --keyring /secure/backup.keyring
```

Validation checks: ZIP structure, per-file SHA-256, manifest parity,
SQLite `integrity_check`, `foreign_key_check`, schema compatibility,
per-table counts, stock-vs-ledger reconciliation, referenced images,
and (for sealed archives) AES-256-GCM authentication.

### 3.3 Restore (planned, shop closed)

```bash
$RETAIL/recoverytool stage --archive /path/to/backup.mlrbak \
  --db /path/to/moonlightretail.db --keyring /secure/backup.keyring
# Restart Retail. The staged restore applies at startup, atomically.
```

The restore is applied during startup **before** the app accepts
business writes. It never runs while Sales are in progress.

**Wrong-Store protection:** a backup belonging to a different Store is
refused. The guard compares the immutable `store_identity` UUID —
changing a shop name is a legitimate restore and is not blocked.

**Post-update safety:** after an updated version has enabled business
operations, automatic restoration of an older pre-update database is
forbidden. Deliberate owner-initiated restore of an older backup is
allowed but warns that newer unbacked transactions are absent.

## 4. PostgreSQL backup and restore (Cloud)

### 4.1 Backup

```bash
$CLOUD/scripts/pg-backup.sh --url "$DATABASE_URL" --out /secure/backups
```

Produces `moonlight-cloud-<timestamp>.dump` (pg_dump custom format),
a schema-only companion, and a manifest with SHA-256 and duration.
Verification is `pg_restore --list` on the produced artifact — a
backup that cannot be read is deleted and reported as failed.

Retention: `PG_BACKUP_RETENTION` (default 7) oldest-first.

> **This is not PITR.** A pg_dump restores to the dump moment only.
> For an RPO tighter than the backup interval the provider must
> supply WAL archiving / snapshot PITR (see §5).

### 4.2 Restore drill (real, disposable)

```bash
# 1. backup
$CLOUD/scripts/pg-backup.sh --url "$URL" --out /backups --label drill-001
# 2. destroy the disposable database
psql "$ADMIN_URL" -c "DROP DATABASE drill;"
# 3. restore
$CLOUD/scripts/pg-restore.sh --url "$URL_RESTORED" --dump /backups/moonlight-cloud-drill-001.dump --force
# 4. start the exact Cloud binary and check /health/ready
```

Post-restore validation runs automatically: schema presence for
devices/stores/sync_events/catalog/sales/admin_users/releases/
update_rollouts, orphan device-binding check, and command PK
integrity.

### 4.3 Point-in-time recovery

**NOT RUN in Phase 20.** PITR requires provider-level WAL archiving
(`archive_mode=on` + a WAL destination) which is external
infrastructure. Resulting limitation: RPO equals the backup interval.

## 5. Cloud outage and resynchronization

Retail is offline-first: POS, inventory, returns and reports keep
working while Cloud is unreachable.

On Cloud recovery:
1. Restore Cloud if needed (§4.2).
2. Restart Retail connectivity — devices reconnect on their own poll
   interval.
3. Retail replays its durable outbox. Cloud reprojects idempotently
   (event IDs and revision checks are preserved).
4. Watch `/api/v1/dashboard/sync-health` backlog drain.

## 5.1 Cloud restore recovery protocol (Phase 20 R2)

A successful `pg_restore` is **DATABASE_RESTORED**, not
**STORE_RECONCILED**. Cloud can serve traffic and return `/health/ready`
200 while its business projections are historically incomplete.

The protocol is explicit and durable:

```text
1. DETECT   scripts/pg-restore.sh marks every device
            RECOVERY_RECONCILIATION_REQUIRED in sync_recovery_state.
            The state is a table: it survives Cloud restarts.

2. EXPOSE   Retail reads GET /api/v1/device-control/recovery/status
            over its normal authenticated control channel. Store sync
            status reports RecoveryRequired=true with instructions;
            pending_outbox=0 is NEVER treated as proof that Cloud's
            projections are complete.

3. VERIFY   Retail walks its RETAINED canonical outbox history in
            bounded keyset pages and POSTs (event_id, payload_hash)
            identities to /recovery/verify. Cloud replies with the
            subset it is MISSING. Identity comparison only - never
            counts, never a fabricated ordering.

4. REPLAY   Retail re-queues the missing rows (bounded, oldest-first)
            and the normal sync worker resends them. Cloud ingest is
            idempotent: duplicates ACK already_accepted; missing
            events ingest and reproject.

5. COMPLETE Retail POSTs /recovery/complete ONLY after a verification
            pass reports zero missing. Until then the device flag
            stays set and the Store is not reported reconciled.
```

Retail is the authority throughout: Cloud never writes Retail Sales,
never fabricates events, never replaces inventory and never reissues a
business mutation. The canonical event bytes are simply re-sent.

**Multi-device rule:** a Store is never labeled reconciled while any
device is still unresolved. Each device clears its own flag.

**Operator actions:**

```bash
# 1. Restore Cloud (this marks the recovery state automatically)
$CLOUD/scripts/pg-restore.sh --url "$URL" --dump /backups/backup.dump --force

# 2. On EACH Retail device, run the reconciliation
#    Retail -> Settings -> Cloud Sync -> Reconcile
#    (CLI: moonlight-retail sync reconcile)

# 3. Verify the flag cleared for every device
curl -s -H "Authorization: Bearer $DEVICE_CREDENTIAL"   https://cloud/api/v1/device-control/recovery/status
#   → {"required": false, "devices_unresolved": 0}

# 4. Only then report the Store as reconciled.
```

**If retained history is unavailable** (the Retail database itself was
replaced and the delivered rows are gone), automatic recovery is
impossible. That case is reported as **recovery-blocked**: the operator
must not be told "fully recovered" when canonical events are missing.

**Retail restored older than Cloud (§7 scenario C):** a restored Retail
backup may lack Sales that Cloud already projected. Those Sales are
**data loss from Retail's side** and are exposed explicitly — the
system does NOT import Cloud projection rows back as new Retail Sales
or inventory movements. The operator must be told plainly that the
transactions are absent from the backup.

## 6. Workstation replacement

```text
1. Install a verified Retail build on the new workstation.
2. Restore the operational backup (§3.3).
   - The immutable store_identity UUID carries over: it is the Store.
   - The old device credential lives in the OS keyring and does NOT
     carry over. Copying the database alone cannot revive a revoked
     device identity.
3. Validate: schema version, integrity check, inventory reconciliation.
4. Re-enroll the device in Cloud (Settings → Cloud Sync → credential).
   Cloud issues a NEW device identity; the old one stays revoked.
5. Reconnect and let sync catch up (§5).
6. Resume Sales.
```

An old revoked device identity must not become usable by copying an
old database — device authorization is server-side and revocation is
authoritative in Cloud.

## 7. Failed update and manual recovery

Phase 18 updater semantics (preserved):

- The updater takes a pre-update SQLite backup and records it in the
  journal.
- The new release runs in a **gated** state: migrations + health check
  + explicit confirmation **before** any business write.
- Rollback restores the previous install and the pre-update database —
  but **only before business operations are enabled**.
- After confirmation, automatic database restore is permanently
  forbidden. A deliberate owner restore is a disaster-recovery action
  (§3.3), not a rollback.

Journal corruption: the agent reports `MANUAL_ACTION_REQUIRED`
(`UPDATE_JOURNAL_CORRUPT`) and the helper refuses to act. The app
still starts normally on the current install.

## 8. OWNER / MFA recovery

All recovery is **CLI-only and audited**. There is no public HTTP
reset endpoint and no way for an ADMIN to gain OWNER privileges.

```bash
# Lost password (and optionally lost authenticator)
$CLOUD/moonlight-cloud auth reset-password --login <owner-login> --reset-mfa
```

Effects: new password set, MFA enrollment cleared (if `--reset-mfa`),
**every** session for that user revoked, `auth.password.reset` audited.

Lost `AUTH_MFA_ENCRYPTION_KEY`:
1. Provision a NEW key (all existing MFA ciphertext becomes unreadable).
2. Set `AUTH_MFA_ENCRYPTION_KEY` and restart.
3. Run `auth reset-password --reset-mfa` per affected user.
4. Users re-enroll MFA and receive new recovery codes.

The system fails closed: it never silently disables MFA or regenerates
credentials because a key cannot decrypt.

## 9. Credential and key rotation

| Asset | Rotation | Notes |
|---|---|---|
| Cloud TLS certificate | reverse-proxy renewal | not persisted in DB |
| PostgreSQL password | `ALTER ROLE` + config update + restart | sessions reconnect |
| Device credential | CLI `device rotate` | old credential revoked in same transaction |
| MFA encryption key | new key + `reset-password --reset-mfa` | old ciphertext unreadable by design |
| Release-signing key | overlapping trusted public keys | see runbook 10 |
| Backup encryption keyring | `AddKey` then re-seal new backups | old backups stay readable; keep the old key |

## 10. Release signing, rollout and revocation

- Generate the Ed25519 signing key **offline**. The private key is
  never packaged into Retail, Cloud or any OCI image.
- Provision the matching public key into Retail builds and Cloud via
  `RELEASE_TRUSTED_PUBLIC_KEYS`.
- Sign release envelopes offline; verify independently before import.
- Roll out through Cloud fleet updates (staged percentage).
- **Revocation:** `SetReleaseStatus` revokes a release; targets stop.
- **Key compromise:** revoke trust in the public key, publish a new key,
  and treat any release signed by the compromised key as untrusted.
- **Key loss:** publishes stop until a new key is provisioned. Existing
  installed Retail keeps working; it cannot be updated.

## 11. Incident diagnosis and support bundle

Collect a sanitized support bundle (Retail):

```
Settings → Diagnostics → Support Bundle
```

Contents: app version/build, OS, schema version, integrity-check
result, error codes, update journal summary. It contains **no**
passwords, tokens, private keys, MFA secrets, recovery codes, provider
credentials or customer records.

Cloud diagnosis: `moonlight-cloud projection status`, `/health/ready`,
`/api/v1/dashboard/sync-health`, `/api/v1/dashboard/update-audit`.

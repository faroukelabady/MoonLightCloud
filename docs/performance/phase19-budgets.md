# Phase 19 — Performance Budgets & Evidence

Scope: prove MoonLight stays responsive, bounded, stable, predictable
and recoverable at realistic data volumes. Correctness outranks
headline numbers; every figure below is evidence-bound to the harness
in `internal/perfbench` (Retail) or the documented measurement (Cloud).

## 1. Budget targets

Budgets are conservative for a normal shop workstation (8-core,
SSD, SQLite) and a modest Cloud server (2 vCPU, PostgreSQL 18). They
are acceptance targets for controlled environments; normal CI only
asserts bounded **statement counts** (`internal/perfbench`), which are
stable on shared runners (§66).

## 4. SQLite query plans / indexes

Captured by `internal/perfbench/plans_test.go` (`EXPLAIN QUERY PLAN`).

| Query | Before | After | Index / change |
|---|---|---|---|
| SKU lookup | `SEARCH product_variants USING INDEX sqlite_autoindex_product_variants_2 (sku=?)` | unchanged | existing UNIQUE index; §10 index-backed requirement holds |
| product list (catalog order) | `SCAN products` + `USE TEMP B-TREE FOR ORDER BY` | `SCAN products USING COVERING INDEX idx_products_catalog_order` | migration `000023_catalog_order_index` |
| product search (LIKE) | `SCAN products` + `USE TEMP B-TREE FOR ORDER BY` | `SCAN products USING INDEX idx_products_catalog_order` | same index removes the sort |
| inventory movement page | `SCAN movement ...` (generic `narg` filter) | `SEARCH movement USING COVERING INDEX idx_inventory_movements_variant (variant_id=?)` | sargable query split (below) |
| movement running balance | `MULTI-INDEX OR` (2 probes/row) | `SEARCH prior USING INDEX idx_inventory_movements_variant (variant_id=? AND created_at<?)` | residual rewrite, provably identical |

Write/storage cost: two additive indexes (`idx_products_catalog_order`
on products, and the existing variant ledger index reused). Product
writes are infrequent catalog edits; the ledger index was already
present. No frozen migration (≤000022) was modified.

## 5. Performance fixes

Every change preserves correctness; none removes a transaction,
revision check, Store filter, permission check or historical snapshot.

### 5.1 `000023_catalog_order_index` (Retail migration)

Added `CREATE INDEX idx_products_catalog_order ON products(created_at
DESC, id ASC)` matching the catalog query's `ORDER BY created_at DESC,
id`. Removes `USE TEMP B-TREE FOR ORDER BY` from every catalog list and
search page. Additive only.

### 5.2 Sargable inventory-movement queries (Retail)

`ListInventoryMovements` used the generic `narg` filter shape
(`? IS NULL OR col = ?`), which the planner cannot turn into an index
seek — it scanned the whole ledger per page (194 ms at 250k rows).
Added `ListInventoryMovementsByVariant` / `ByProduct` (and matching
count twins) with plain equality predicates; the repository dispatches
on the scope it already has. The UI is always variant- or product-
scoped, so both paths are now index-backed. **Semantics are identical:**
same columns, same filters, same ordering, same running-balance result.

### 5.3 Running-balance residual rewrite (Retail)

The per-row running-balance subquery used
`created_at < ? OR (created_at = ? AND id <= ?)`, planned as
`MULTI-INDEX OR` (two index probes per returned row). Rewritten to
`created_at <= ? AND (created_at < ? OR id <= ?)` — provably the same
result set (truth table: rows strictly before, or equal-timestamp with
`id <=`) but planned as a single index range.

### 5.4 Batched admin-command device annotation (Cloud)

`annotateCapabilities` issued up to 5 statements per command target
(`DeviceActive` + `BindingStore` + `GetCatalogAdminCommand` +
`GetCatalogAdminCapability` + `DeviceName`) — an N+1 that scaled with
target count. Replaced by one set-based
`CatalogAdminDeviceStates(device_ids)` read plus one command read per
distinct command. Same behavior: same skip rules, same capability
labels, same Store-scope rejection.

### 5.5 `00043_projection_discovery_index` (Cloud migration)

`PendingCatalogEvents` / `PendingSaleEvents` / `PendingReturnEvents`
order by `(received_at, event_id)` on the sync inbox; only
`(device_id, received_at)` was indexed, so discovery sorted the whole
matching inbox per scan. Added `idx_sync_events_received(received_at,
event_id)`. Additive only; migrations ≤00042 byte-identical.

## 6. Bottlenecks not fixed

| Item | Classification | Evidence / rationale |
|---|---|---|
| Product search `LIKE '%term%'` over names + translations (54 ms p95 at 10k products) | accepted production-scale limitation | Non-sargable contains-search. The sort cost is gone (index), remaining cost is the scan + translation joins. A proper fix is SQLite FTS5, which adds schema surface and segmentation rules that §12 forbids assuming for Arabic. Management search, not POS; within the 250 ms budget. |
| Offset pagination at very large page depth (product list middle 11 ms at 50% depth on 10k) | future growth concern | Bounded and budget-compliant today. Keyset pagination would change the API contract (§13) — deliberately deferred rather than risk a contract break in a performance phase. |
| Movement `resulting_stock` is computed per returned row | accepted production-scale limitation | Provably correct and now index-range-backed (0.18 ms p95). A precomputed running-total column would be a schema change and a correctness risk to the ledger. |
| Large-profile seeding time | Note | `perfdata` Large (1M movements) is a dev tool; generation cost is not an application cost. |
